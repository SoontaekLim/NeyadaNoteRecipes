# NeyadaNote 공식 레시피 분류 표준 (v1)

이 문서는 **NeyadaNoteRecipes의 공식 레시피**에 적용하는 분류 규칙이다. 목적은 레시피 수가 증가해도 검색과 탐색에 일관성을 유지하는 것이다. 일반 사용자가 앱에서 만든 맞춤 카테고리를 제한하지 않는다.

## 핵심 원칙

1. 물리적 경로는 기존 `recipes/<recipe-id>/`를 유지한다. 카테고리별 하위 폴더를 만들거나 공개된 레시피 ID를 바꾸지 않는다.
2. `recipe.json`의 기존 `tags` 배열을 사용한다. **첫 번째 태그는 아래 5개 기본 카테고리 중 정확히 하나**로 한다.
3. 두 번째 태그는 음식 문화(선택), 세 번째 태그는 용도(선택)로 사용한다. 새 공식 레시피는 기본적으로 **1~3개 태그**를 권장한다.
4. 분류는 주재료가 아니라 **일반적인 제공 형태와 식탁에서의 역할**을 기준으로 결정한다. 같은 레시피에 기본 카테고리 두 개를 넣지 않는다.
5. `ko-KR`과 `en`은 같은 분류 의미와 태그 순서를 유지하되 각 언어의 표준 표기를 사용한다.

## 기본 카테고리 (필수, 정확히 1개)

| ko-KR 저장값 | en 저장값 | 적용 기준 | 예시 |
| --- | --- | --- | --- |
| `메인 요리` | `Main Dish` | 식사의 중심을 이루는 고기·생선·두부 등 주요 접시 요리. 단, 한그릇·면·국물요리는 각각의 전용 카테고리를 우선한다. | 소불고기, 제육볶음, 닭갈비, 스웨덴식 미트볼 |
| `반찬` | `Side Dish` | 밥이나 다른 메인 요리에 곁들여 먹는 요리. 밑반찬과 비교적 푸짐한 반찬을 모두 포함한다. | 계란말이, 멸치볶음, 나물무침 |
| `국/찌개` | `Soup/Stew` | 국, 찌개, 수프처럼 국물이나 떠먹는 스프가 중심인 요리. | 미역국, 김치찌개, 감자스프 |
| `한그릇요리` | `One-Dish Meal` | 밥·김밥·덮밥·볶음밥 등 한 접시나 한 그릇으로 식사가 완결되는 요리. 반드시 그릇에 담겨야 하는 것은 아니다. | 김밥, 볶음밥, 카레라이스 |
| `면요리` | `Noodles/Pasta` | 국수·파스타·라면 등 면이 중심인 요리. 국물 있는 면도 여기에 포함한다. | 까르보나라, 잔치국수 |

### 기본 카테고리를 선택하는 순서

- **면이 주인공**이면 `면요리`, **밥이나 김밥 등으로 한 끼가 완결**되면 `한그릇요리`로 분류한다.
- 그 외 **국물·스프가 주인공**이면 `국/찌개`로 분류한다.
- 나머지 접시 요리는 일반적으로 **식사의 중심**이면 `메인 요리`, **곁들이는 음식**이면 `반찬`으로 나눈다.
- 애매한 요리는 가장 일반적인 제공 방식을 선택하고, 선택 근거를 PR에 남긴다. `메인 반찬`처럼 두 기본 카테고리를 합친 별도 분류는 사용하지 않는다.

## 보조 태그 (선택)

### 음식 문화: 0~1개

| ko-KR | en |
| --- | --- |
| `한식` | `Korean` |
| `중식` | `Chinese` |
| `일식` | `Japanese` |
| `양식` | `Western` |

전형적인 음식 문화가 명확할 때만 붙인다. `양식`은 현재의 넓은 서양식 분류이며, 출신 국가를 억지로 하나의 문화로 결정할 필요가 없다. 범주가 불명확하면 생략한다.

### 식사 상황: 0~1개

현재 허용하는 식사 상황 태그는 `야식`(`Late-Night Food`), `술안주`(`Food with Drinks`)이다. 해당 용도로 뚜렷하게 쓰이는 경우에만 붙인다. 기본 카테고리를 대신할 수 없다.

매운맛·채식·조리 시간·난이도·주재료 등은 현재 별도의 통제 어휘로 정의하지 않는다. 검색 수요와 일관된 판정 기준이 생긴 뒤 별도 개정으로 도입한다. 새 공식 태그를 임의로 만들지 않는다.

## JSON 작성 예

한국어 기본 레시피:

```json
"tags": ["국/찌개", "양식"]
```

같은 레시피의 영어 번역:

```json
"tags": ["Soup/Stew", "Western"]
```

각 locale의 `README.md` 분류 표시는 해당 `recipe.json`의 태그와 일치해야 한다.

## 기존 데이터와 앱 호환성

**이 문서는 분류의 목표 상태를 정하는 것이며 기존 레시피·앱 데이터를 자동 변경하지 않는다.** 현재 공식 레시피와 앱에는 이전 명칭이 섞여 있다.

| 이전 표기 또는 사용 사례 | 표준화 방향 |
| --- | --- |
| `메인요리` | `메인 요리` |
| `밑반찬` | `반찬` |
| `메인반찬`, `메인 반찬` | 실제 역할에 따라 `메인 요리` 또는 `반찬` 중 하나를 판단 |
| `메인 요리` + `면요리` (까르보나라) | 기본 카테고리를 `면요리` 하나로 정리 |
| `메인 요리` + `한그릇요리` (카레라이스) | 기본 카테고리를 `한그릇요리` 하나로 정리 |
| 영어 `Main dish`, `Main Dish` | `Main Dish`로 통일 |
| 영어 `Pasta` | 기본 카테고리 `Noodles/Pasta`로 통일 |
| 영어 `Rice Dish` | 기본 카테고리 `One-Dish Meal`로 통일 |

앱에는 `메인요리`, `메인반찬`, `밑반찬` 등의 기존 카테고리 저장값과 문자열 일치 기반 필터가 존재한다. 따라서 **기존 레시피 태그만 먼저 대량 치환하면 카테고리 탐색이 깨질 수 있다.**

향후 별도 변경에서:
1. 앱의 기존 저장값과 공식 태그를 정규화하는 호환 별칭을 추가하고, 영어 locale 태그도 의미 기준으로 연결한다.
2. 이전 사용자 카테고리와 이미 저장된 레시피는 보존한다.
3. 앱 호환성을 확인한 후 기존 공식 레시피의 ko-KR/en 태그를 함께 표준화한다.
4. 필요할 때 신규 공식 레시피의 기본 카테고리·번역 대응을 점검하는 자동 검증을 추가한다.

## 확장 및 버전 관리

레시피 수가 늘더라도 `recipes/<recipe-id>/`와 공개 ID는 유지한다. 기본 카테고리 추가나 분할은 기존 5개 어디에도 적절히 들어가지 않는 새로운 요리군이 생겼을 때 별도 PR에서 사례·호환성·번역을 검토한 후 진행한다. 예를 들어 `간식/디저트`는 실제 공식 레시피가 등록될 때 확장할 수 있다.

이 문서는 공식 레시피의 **메타데이터 분류 규칙**이다. 앱 UI의 카테고리 메뉴, 사용자 정의 카테고리, 원격 카탈로그의 분할·페이지네이션 등 구현 변경은 별도 작업으로 다룬다.
